# Network-site tasks: devblog, micro, makers

Generated tasks for the three network sites that share the social database with the community site
(`sites/social`): devblog ("Byteline", long-form articles, network 2), makers ("Workbench", builders
and their products, network 3) and micro ("Murmur", short posts, network 4). One generator covers all
three: templates per site in `<site>.js`, shared helpers in `lib.js`. Output: `tasks/<site>/generated.jsonl`
(1,259 / 1,507 / 919 tasks, 53 templates). The row format is the generated-task format of the other
sites (docs/GENERATOR.md), with `start_url` placeholders `__DEVBLOG__`, `__MICRO__`, `__MAKERS__` and
`login_user` = the account's network handle.

```
node tasks/net/gen/index.js --site all --seed 1          # -> tasks/{devblog,micro,makers}/generated.jsonl
node tasks/net/gen/index.js --site micro --list          # templates: kind, id, skills, difficulty
node tasks/net/gen/check.js --site devblog [--advance 6] # references re-derive, decoys / untouched state fail
node tasks/net/gen/solve.js --site devblog [--per 2]     # write templates done through the site's forms, graded
node tasks/net/gen/ui-check.js --site devblog --per 3 --advance 0,6   # read templates answered from headless Chrome
```

The database is read from `$WSB_DATA_ROOT/devblog/base.db` (`WSB_DEVBLOG_DATA` overrides the directory);
devblog, micro and makers all point at the same social `base.db`. `index.js` caps a template at 80 tasks
(`--max`, or a template's own `max`), drops duplicate intents, and checks that every `login_user`
resolves to its account on that network.

## How the tasks stay valid while a rollout runs

The tenant clock starts at `site_settings.social_now` and runs with real time, and each site fires its
own network's scheduled world events as it moves (new articles, posts, comments and replies). So:

- samplers skip every entity a scheduled event will touch (`sched(net)` in `lib.js`);
- "this week" / "last N hours" windows stay at least 6 h away from their edge, so a reference holds for
  the whole rollout;
- rows the agent creates carry the tenant clock (at or after `social_now`), and state checks look only at
  those (`since()`), so world events never satisfy a write task.

`check.js --advance H` moves the clock H hours and requires every answer task's SQL to still give its
reference; `ui-check.js --advance 0,6` answers each read task from the rendered pages at both offsets.

## Checks

| Script | What it proves |
|---|---|
| `check.js` | every `login_user` logs in as the intended account; answer SQL re-derives the reference; the reference passes; an empty answer, a decoy and a "list every number" answer fail; `must_exclude` decoys fail; state checks fail on the untouched tenant |
| `solve.js` | each write template can be done through the site's own forms (the requests its UI sends) and then passes; tenant reset between tasks |
| `ui-check.js` | each read template can be answered from what headless Chrome renders (tabs, filters, links, pagination), the site grader passes it, and a wrong answer fails. Results: `tasks/<site>/verify-generated.jsonl` |

Widget variants of these tasks (docs/WIDGETS.md) are generated by `tasks/variants/` from these rows.

The `dm-*` templates (`micro-dm.js`, appended after the others so their seeded draws are unchanged)
read the world's direct messages (`sites/social/build/dms.js`): unread state from the `message`
notifications, the opening message's facts and the post a conversation is about from the hidden
`world_dm_threads`. No scheduled event touches a conversation; opening one marks it read, but answers
are fixed at generation. Fact answers accept other spellings of a time ("6:30pm" / "6:30 pm").
